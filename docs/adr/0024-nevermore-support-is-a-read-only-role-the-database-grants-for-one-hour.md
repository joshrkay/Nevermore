# Nevermore support is a read-only role the database grants for one hour

Status: accepted. Builds on D-16 (a platform admin is no member of any firm), D-18 and D-40 (the database is the lock; the address only narrows), D-19 (a password sign-in owes its second factor), D-33 (a firm never sees who at Nevermore acted) and ADR 0023 (the one guard every write path shares). Settles CRM-P2.4.

## Context

A platform admin reads none of a firm's data (D-16). Support still needs one doorway: to look at what a firm's owner sees, to answer "why is my quote stuck". It has to be narrow (read only, one firm, one hour), it has to be on the firm's record, and the firm must never learn which person at Nevermore looked (D-33).

Almost every policy and function asks a membership helper (`firm_role`, `is_firm_member`, `intake_in_my_firm`, `quote_request_in_my_firm`, `intake_folder_in_my_firm`, `can_read_firm_activity`, `can_read_peo_mail`), 85 functions and the policies on 28 public tables and 3 storage buckets (counted when this was written, from `pg_proc` and `pg_policies` on a migrated database: the functions whose source names a membership helper or `require_advisor`, and the tables and buckets with a policy that does). Two ways to give support the read side were weighed:

1. **A small set of explicit support read functions** (the queue, a submission, members, activity) that check the session themselves and leave every helper alone. Narrowest in what it touches, but every screen would need a second, support-only way to load its data, and the next story's screen would too.
2. **One new value from the helper everything already asks.** `firm_role` answers `support` for a caller with an open, unexpired session for that firm. Nothing that asks for a role by name (`'owner'`, `'lead'`, `'agent'`, `= ANY(...)`) lets `support` through; what lets it through is what only asks "is a member" (`firm_role IS NOT NULL`, `is_firm_member`): the reads. The workspace's screens work unchanged.

We chose 2. What made it sound is that ADR 0023 had already put every write behind one guard: each function that changes a firm's data calls `assert_firm_writable`, one table has a trigger that calls it, and two storage policies call a helper that does. A standing test fails on a write path that is neither guarded nor exempt with a reason. So the work was to refuse a support session in that one place, extend the standing test, and re-examine every exempt path. `supabase/tests/help_from_nevermore.sql` also lists every function and policy that asks a membership helper and fails on one that is not classified as a read, a write, an owner-only action or the caller's own.

## Decision

- **A session** (`support_sessions`, closed to the API): who (id and email, the platform's alone), which firm, the reason (1 to 500 characters, required), started, ends (exactly one hour later, by a check; the server's clock), ended and how (`ended`, `ran_out`, `firm_ended`, `became_member`). One open session per admin per firm is a unique index (D-29). Admins start and end through `start_support_session` and `end_support_session`, and read the list through `admin_support_sessions()`, as `admin_firm_states()` does for firms.
- **What grants the read side** (`support_reads_firm`): an open session of the caller's own, a signed-in platform admin past their second factor, a request that names that firm's address (so the bare domain gives nothing), a firm that is not refused and not closed. A suspended firm is allowed: that is when it needs looking at, and it is reads only. A closed or refused firm ends the session at that moment, because the question stops answering yes.
- **What every refusal asks** (`is_support_session`): wider on purpose (an open session, any address, any other fact): refusing too much a person with no membership costs nothing; refusing too little would.
- **What support reads**: what an owner reads, which is what any member reads (the queue, a submission and its mail thread, notes, referral partners, the document rows) plus the members (`firm_members`) and the firm's record (`can_read_firm_activity`). Not the invitations, requests to join or listed organisations (people who are not members yet). No secret: a mailbox's token is read only by the mailbox function for a member in good standing, and an invitation's token is never kept, only its hash. **No file and no download**: a downloaded file leaves the product and the hour. In the database, `intake_folder_in_my_firm` and the PEO attachment policy refuse a support session, so no stored file opens (documents, stored packets, PEO attachments). In the screens, no download control is offered in the firm's workspace during a session (the ones that build a file in the browser from rows support may read, and the ones that open a stored file), with one plain line, "Downloads are off during Nevermore support.", where a group of them was; the rows still say a file is there. The employer's own pages are not the firm's workspace and are unchanged. This second rule is a **screen rule**, not a database rule: a person with the rows on their screen can still copy them, and a browser-built file leaves no entry in the firm's record, because `record_member_activity` refuses support. That is why it is not offered, and why the next story that adds a way to take rows out must ask the database, not the screen.
- **What support cannot do**: every guarded write refuses it with "Nevermore support can look, not change" (PT423), restated in `assert_firm_writable` with every rule and lock it had. The three paths that looked like reads and wrote were fixed: `record_member_activity` refuses it, `advisor_open_quote_request_thread` marks nothing for it (the mark holds the opener's email, which the firm's members read), and `open_submission` still writes the opening, as Nevermore's, which is the firm's record of the use.
- **Sends and exports**: every send path is a guarded write, and the mailbox function asks `my_firms()` and `person_is_member_of_a_firm_in_good_standing`, which are membership questions a session is not an answer to (tested). Exports do not exist yet (CRM-S3.8b, D-48): `refuse_support_session(firm)` is the helper its export function must call first. A test calls every function the API roles can run with `export` anywhere in its name, as a support session at the firm's address with fixture arguments, and fails on one that does not raise PT423 (a function whose arguments cannot be guessed is read as text and must call the helper with a firm, not NULL). `refuse_support_session(NULL)` cannot say which firm, so it refuses a caller who holds any open session: passing NULL fails closed.
- **Each use in the firm's record** is two entries of kind `support_access`, written as Nevermore's whatever the admin's role is by then (stamped true at the write, so a session recorded after its admin lost the role cannot show their email): a start (record type `support_session`) and an end (`support_session_end`), each carrying the session's id. The owners read the reason and the times through `firm_support_sessions(firm)`, never who. The real actor is stored in the entry's `actor_id` (a column no API role can read) and in the platform's table.
- **Becoming a member ends it.** An admin who accepts an invitation to the firm, or whose request to join an owner approves, while their session is open has their session ended in the same transaction (`became_member`, in the firm's record as Nevermore's like any other end). Otherwise they would hold a role and be refused every write for the rest of the hour, because the guard refuses an open session first. `start_support_session` already refuses a member.
- **Ending** is recorded when it is next seen (starting another session, ending, the Firms page, the firm's address) or by the daily job (`settle_support_sessions`, a step of the firm record's job). What stops a session is the clock in `is_support_session`, so one nobody has looked at stops all the same. A session that ran out is recorded at its end time, not at the time someone looked.
- **A password sign-in** owes its second factor first (D-19): the session grants nothing until it is done. `my_support_session_here` answers before the second step, saying it is pending, so the page sends the admin to the step and not to "You aren't a member of this firm".
- The monitoring table gains one kind, `support_access`, written when a session starts. It has no alert rule: a use is not a failure.

## Consequences

- The role `support` is handed out only by `firm_role`. Three reads name it, to treat it as an owner reads: `can_read_firm_activity`, `firm_members` and `can_see_firm_record` (the one question every owned record will ask, so support sees what an owner sees at either visibility setting). A later story that lists roles by name must not add it; a test fails if any other function says the word.
- A story that adds a function that changes a firm's data adds it to the guarded or exempt list of `close_a_firm.sql` and `help_from_nevermore.sql`, and the second asks "why can a support session not use it".
- Support sees the owners' reading screens, and the screens hide what is cheap to hide (the member actions, "Leave this firm"). Controls that write can still be visible; the database refuses them and the message is shown.
- A support session is bound to the admin's own sign-in and to one firm at that firm's address. It gives nothing to another admin, nothing at another firm's address, and nothing on the bare domain.
- Known limits: the no-download rule in the screens is a screen rule (above): rows on the screen can be copied, and the database's own guarantee is that no stored file opens. `report_client_event` records a browser failure with the admin's id against an intake they can read, in the platform's monitoring table only.
