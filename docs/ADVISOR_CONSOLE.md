# The Advisor Console as the operating workflow

The advisory team works Submissions in the Advisor Console (`/advisor`), not in a separate CRM
(decision D6). Every Submission appears there the moment its prospect certifies it. Nothing is
re-keyed and nothing is synced anywhere else. This page is the field mapping and ownership rules
US-5.3 asks for. Who may open what is in `docs/ADVISOR_ACCESS.md`, and the terms are in
`GLOSSARY.md`.

## Where each core field lives

| Field | Where advisors see it | Source | Owner |
|---|---|---|---|
| Company | Queue and submission page | The prospect's answer (`company_name`), else the company on their profile | Prospect |
| Contacts | Submission page: the signer and their title (from the certification), and the profile's contact name and phone. The queue shows the contact's name only. The account's email is in the Advisor Alert but not in the console (see "Known gap") | Certification, profile, account | Prospect |
| Employee count | Queue and submission page | The prospect's answer (`employee_count`) and the census | Prospect |
| Locations | Queue: the state footprint (states of operation plus the census's work states). Submission page: HQ state and states of operation | The prospect's answers (`hq_state`, `states`) and the census | Prospect |
| Status | Queue (filterable) and submission page, with its history | `submission_workflow`, `submission_status_history` | Advisors, except the two automatic moves below |
| File ID | Queue (searchable), submission page, both emails, the Manuscript | Assigned by the database the first time the Intake is certified: `EAA-<year certified, UTC>-<number from that year's sequence>`, unique, and kept for good; the queue shows "No File ID yet" for a draft. An Intake certified under the older rule keeps the File ID its certification recorded | Nobody edits it |
| Manuscript | The prospect's signed Manuscript, and the advisor-reviewed versions on the submission page | The certified answers; versions are generated by advisors into the private `manuscripts` bucket | Advisors generate versions; a recorded version can't be overwritten or deleted |

## Ownership rules

- **The prospect owns the answers.** Advisors read them but cannot change them. A correction is an
  advisor field review stored beside the answer (`advisor_field_reviews`, every change appended to
  `advisor_review_events`), and it reaches the advisor-reviewed Manuscript, not the prospect's
  record.
- **A prospect changes a Submission only by certifying again.** Changed answers withdraw the
  certification until they are certified again. The new certification is the next numbered version of
  the Submission (each version keeps its own copy of what was certified), keeps its File ID, and sends
  an "Updated Intake" Advisor Alert.
- **Advisors own the pipeline status.** They change it only through `set_submission_status()`, which
  records who, when, from, to and why, and moves it one step at a time: only to a stage the allow-list
  names for the current one (`docs/ADVISOR_ACCESS.md`). The system makes two moves itself. Certifying moves a draft
  to `submitted`. A withdrawn certification moves `submitted` back to `draft`, but only while no
  advisor has moved it on.
- **Advisors mark what needs action.** Any submission can be marked "Needs advisor action" with a
  note, through `set_submission_needs_action()`; the queue shows it and can list only those. It is
  recorded in the status history and never shown to the prospect.
- **Advisors own notes.** Notes are internal, can't be edited or deleted, and prospects never see
  them.
- **Every Submission is worked.** There is no qualifying step; the status is the team's triage.

## Links

No link that is stored, emailed or logged opens a document.

- The Advisor Alert links to `/advisor/submissions/<intake id>`, which needs advisor sign-in.
- Uploaded documents and Manuscript versions open through signed links that last 60 seconds. They
  are created when an advisor clicks and are never stored.
- The prospect's Manuscript page (`/manuscript/<File ID>`, and the older `/manuscript?session=<intake id>`)
  is protected by row security: only the intake's owner and advisors can read it, so the address alone
  shows nobody else anything. It renders the certification's own copy of the answers, never the live draft.

## Failures

Nothing syncs, so there is no sync to fail. The emails about a Submission (the Advisor Alert and the
Confirmation) can fail; they are retried, logged, and shown with a retry button on
`/advisor/outbox` (`docs/NOTIFICATIONS.md`).

## Known gap

The console does not show the account's email, which is where the Confirmation goes and the
address a prospect signed in with. Advisors have it from the Advisor Alert only. The submission page
shows the phone on file, and says so when the Confirmation bounced.

## If a CRM is added later

Send it through the outbox, as the emails are: a new event kind queued in the certification
transaction, with retries, an advisor retry on the Outbox page, and one record per Submission. Key
the record on the intake id, not the File ID, which is assigned by the database at the first
certification and never changes (D15). Send the CRM the sign-in link above, never a signed storage
link.
